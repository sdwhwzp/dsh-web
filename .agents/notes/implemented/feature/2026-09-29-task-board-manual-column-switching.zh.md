# Agent Note: 任务看板的手工列切换

Status: implemented

## Problem

看板的五列原先有两个属主：`backlog`（待规划）与 `todo`（待办）属于操作者；`running`（进行中）、`done`（已完成）与 `failed`（已失败）属于执行器。`MANUAL_STATUSES` 是 `['backlog', 'todo']`，而每一处表达「这张卡归执行器所有」的守卫与控件都写成 `status === 'running'`：账本的移动/删除/归档/执行拒绝、级联参与者筛选、改挂父任务的锁、拖拽源、执行按钮、子任务解除关联锁、卡片转圈。

这一划分假定卡片状态由 Host 启动的会话产生。但看板上存在不由会话完成的工作：交给外部代理机构提交的专利、由人工投稿的论文、在会议上定下的评审、手工执行的测试。这类卡片能被标成「待办」或「已完成」，却永远无法标成「进行中」——看板只有在 Host 自己跑东西时才显示进行中，于是追踪外部工作的操作者只能在「低报」和「谎报」之间二选一。

仅仅放开这一列并不够。如果 `running` 变成普通列而守卫继续读列，手工停在该列的卡片会变得无法收拾：`run` 拒绝它（看起来正忙），`move` 拒绝它，`archive` 与 `delete` 拒绝它，`settle` 也拒绝它——因为它没有未结算的执行可供关闭。锁必须先离开列文本，列才可能自由。

## Decision

卡片可以手工移到除当前列以外的任意列。「这张卡归执行器所有」的含义是存在未结算的执行记录，而不是列文本。

### 一个谓词，三个面

- `MANUAL_STATUSES` 即全部状态。`canMoveManually(from, to)` 接受任何非当前列，`canMoveTask(task, to)` 再加上两个决定「到底能不能移」的条件：卡片在看板上、且没有未结算的执行。`canMoveTask` 是「这张卡能否移动」的唯一属主，因此账本、详情页状态行与看板落点不可能互相矛盾。
- `hasOpenExecution(task)` 从 `host-ledger.ts` 的私有辅助函数移入 `core/tasks.ts`，浏览器半区同样可达。
- agent 工具面暴露 `move-backlog`、`move-todo`、`move-running`、`move-done`、`move-failed`，五者都映射到同一个 `move` 协议动作；该动作本就携带 `TaskStatus`，线上格式不变。

### 锁在执行，不在列

所有原先读 `status === 'running'` 的守卫改为读 `hasOpenExecution`：账本的移动、删除、归档/恢复的子树检查、执行/重跑与 cron 触发门禁、级联参与者筛选与启动、改挂父任务锁，以及重启对账。浏览器半区同样如此：拖拽源、卡片转圈、执行按钮、标签编辑、子任务解除关联锁、子任务汇总的「进行中」计数与可关联候选列表。

于是手工停在进行中列的卡片一切照旧可用：可移动、可归档、可改挂、可删除、可编辑、可执行——执行会开启真实 execution，并以记录到的结果结算该列。持有未结算执行的卡片则与从前一样全部拒绝，`settle` 仍是看板已无法观察的那种卡片唯一的出口。

重启对账去掉了 `status === 'running'` 前置判断：重启或导入后仍没有会话 id 的未结算执行一律判为 cancelled（fail closed），无论卡片显示在哪一列。因此持久化的「无会话执行」不再能通过导入存活；运行时视图提供的「等待会话」投影由真实启动产生。

### 是声明，不是已记录的判定

手工移动只经 `withStatus` 写入列，别的什么都不做：不产生执行记录、不动计划、不碰执行历史。`done`/`failed` 声明工作在 Host 执行之外结束（或失败），`running` 表示工作正在进行但没有对应会话。卡片的执行列表仍能区分两种来源，下一次结算的运行会用记录到的结果覆盖该列，持久化格式不变（`schemaVersion` 仍为 4，无迁移）。

## Alternatives considered

**保留 running 归执行器，只放开规划列与判定列。** 否决：这会让「确实在进行中」的工作无法表达，而这正是本次诉求——追踪 DSH 之外工作的操作者只能选一个低估或高估的列。

**把 `running` 当普通列放开，但守卫继续读列。** 否决：手工停在该列的卡片会无法收拾（跑、移、归档、删除、settle 全部拒绝，且没有 execution 可供 settle 关闭）。放开列与移走锁是同一件事，不能拆成两步。

**为手工状态新增持久化来源字段。** 否决：账本格式有版本，该字段需要加载时归一化、并在下一次结算运行时清除，且每位读者都要学会它。执行历史本身已把声明与运行分开。

**给手工停在进行中的卡片单独的标记或色调。** 暂时否决：详情页本就显示是否存在执行，而持久化标记还得由覆盖该列的结算路径负责清除——多一份状态，不多一分事实。

## Consequences

- 五列都可手工切换：看板拖拽、详情页状态按钮与对话中的 `task_board_manage`；三个面一起放行，也一起拒绝。
- 进行中列承载两种含义：Host 正在执行（有未结算执行、有会话、有转圈）与操作者手工声明的进行中（无执行）。详情页的执行列表用于区分。
- 持有未结算执行的卡片锁定行为与消息完全不变。
- 导入不再保留「无会话的未结算执行」，这类行在启动时被判 cancelled，而不是作为无法观察的运行残留。
- 内容编辑的冻结时机从「处于 running 列」改为「出现第一条执行记录」，因此手工停在 running 的卡片仍可修正内容。

## Testing

`tests/tasks.spec.ts` 钉住两个谓词（任意列可达，当前列与执行中/已归档卡片被拒），`tests/host-ledger.spec.ts` 手工把卡片停进 `running` 再移回、记录手工 `done` 时执行历史为空，并在导入归一化改变后改用真实启动驱动运行时投影，`tests/controller.spec.ts` 执行手工停在 running 的卡片、并在有未结算执行时仍拒绝二次启动，`tests/agent-tools.spec.ts` 经工具面驱动 `move-done` 并断言 `executionCount` 仍为 0，`tests/board-view.spec.tsx` 把卡片投到「已完成」与「进行中」列，同时拒绝拖拽执行中的卡片。包级 typecheck、测试与构建通过，`pnpm docs:check` 与 `pnpm i18n:check` 同时通过（移动文案已镜像进俄语字典）。
